# Unity Editor Touch Bridge — 远程控制稳定性问题与解决路径

## 1. 当前项目遇到的问题

### 1.1 现象

- 在手机端浏览器查看 Unity Game View 时，偶发出现"画面冻结但连接未断"。
- 冻结后即使客户端触发重连，有时仍会再次进入卡死状态。
- 该问题在网络抖动、设备性能较低、帧率较高时更容易复现。

### 1.2 根因（协议层）

当前方案是：

- 视频：`WebSocket (TCP) + JPEG 帧序列`
- 控制：同一 WebSocket 上行触控 JSON

其核心缺陷是 **TCP 队头阻塞（Head-of-Line Blocking）**：

1. 某一帧发送/重传变慢后，后续帧必须排队等待；
2. 视频流属于"时效数据"，旧帧应该被抛弃，但 TCP 强制可靠有序，不允许跳过；
3. 最终表现为延迟累积、卡顿、冻结；
4. 即使连接层仍存活（Ping/Pong 正常），逻辑上也可能长期看不到新帧。

结论：这是架构级问题，不是单点代码 bug。

---

## 2. 与云游戏、Chrome、其他远程控制产品的区别

### 2.1 云游戏/远控产品主流方案

行业通用技术栈是：

- **WebRTC / RTP / UDP** 作为实时媒体传输层；
- **H.264 / VP8 / VP9 / AV1** 作为视频编码；
- **RTCP + 拥塞控制 + NACK/FEC** 作为弱网恢复机制；
- 客户端通常走硬件解码，低时延且功耗可控。

这些机制的共同目标是：**宁可丢旧帧，也不阻塞新帧**。

### 2.2 Chrome Remote Desktop 的关键点

- Chrome Remote Desktop 底层走 WebRTC 路径（现代浏览器能力）。
- 实时视频不是"WebSocket 推 JPEG"。
- 连接建立后，媒体通道具备自适应码率与抖动缓冲能力，能在抖动下保持可用。

### 2.3 本项目与主流方案对比

| 维度 | 本项目当前 | 云游戏/CRD/成熟远控 |
|---|---|---|
| 视频协议 | WebSocket over TCP | WebRTC/RTP over UDP |
| 视频编码 | JPEG（帧内压缩） | H.264/VP8/VP9（帧间压缩） |
| 弱网表现 | 容易累积延迟并冻结 | 可自适应码率并丢弃旧帧 |
| 恢复能力 | 主要靠重连 | 协议内恢复 + 自适应 |
| 端到端时延 | 较高且波动大 | 更低且更稳定 |

## 3. 为什么"继续修补 WebSocket + JPEG"无法彻底解决

已尝试或可尝试的手段（异步发送、丢帧、心跳、超时重连）只能降低概率，无法根治：

- 这些手段发生在应用层；
- 根因在传输层（TCP 有序可靠语义）与媒体层（JPEG 非实时流协议）不匹配；
- 因此只能做"缓解"，不能做到"彻底稳定"。

---

## 4. 若要彻底解决，应如何做

## 4.1 技术方向（唯一根治路径）

将视频链路升级为 **WebRTC 实时媒体链路**，WebSocket 仅用于信令或控制通道。

推荐目标架构：

1. 视频下行：`RTCPeerConnection`（WebRTC 视频轨）
2. 触控上行：`WebRTC DataChannel` 或保留当前 WebSocket JSON
3. 服务端：增加 SDP/ICE 信令交换逻辑
4. 编码：优先 H.264（移动端兼容最好）

## 4.2 关键实现要求

- 支持动态码率、动态分辨率、关键帧请求（PLI/FIR）
- 拥塞控制与网络状态反馈（RTCP）
- 客户端渲染链路支持硬件解码
- 明确区分"实时数据"与"可靠控制数据"通道

## 4.3 iOS 约束（当前决策中的决定性因素）

本项目目标包含 iOS 浏览器端控制。当前关键限制：

- iOS Safari 对 `getDisplayMedia` 捕获外部应用窗口能力受限（无法作为通用方案）
- 这意味着"仅靠浏览器抓屏 + WebRTC"在 iOS 上不可作为最终解

因此，要想在"必须支持 iOS"前提下彻底解决，通常需要：

- 引入原生端能力（App/SDK）承担媒体采集与编码；或
- 使用成熟远控/串流 SDK（含 iOS 完整支持）；或
- 调整产品目标，放弃纯浏览器 iOS 端无插件方案。

---

## 5. 结论与项目定位建议

### 5.1 结论

- 在"纯浏览器 + WebSocket + JPEG + iOS 必须支持"约束下，无法达到云游戏/Chrome 级稳定性。
- 若坚持当前架构，项目应定位为研究/演示工具，而非生产级远控方案。

### 5.2 可选路线

1. **研究项目路线（当前推荐）**
   - 保持现有实现，文档中明确已知限制与适用边界。

2. **产品化路线（需重构）**
   - 迁移到 WebRTC + 视频编码体系；
   - 同时为 iOS 提供原生采集/解码能力或采用第三方成熟 SDK。

---

## 6. 给使用者的透明说明（建议放入 README）

- 本插件当前实现为 Editor 研究工具，视频链路采用 WebSocket + JPEG；
- 在网络抖动场景下可能出现冻结或明显时延上升；
- 如需生产级稳定低时延远控，请评估 WebRTC/原生 SDK 路线。
